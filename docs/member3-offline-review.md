## 程式問題

### F1 P1 重建報告會遺失必需成本圖表

位置：`member3_extension/deliver.py:121`。`main()` 直接以內建字串覆寫正式報告與 summary，沒有載入新成本基準或呼叫繪圖整合。以攔截所有寫入的方法執行生成器：現存報告有 `update_cost_comparison.png`，生成內容卻沒有圖，也沒有 0.8849／0.6130 的 30 次量測表。這是會在重新交付時使所需成本內容消失的真實功能缺陷；目前已保存的報告和 ZIP 仍包含圖表。

建議：將成本節加入正式生成流程，由 `benchmark.json` 統一產生，或在生成器中明確整合既有成本節；為重建後仍保有圖與量測表加入回歸測試。

### F2 P2 評分審計沒有核對原始回覆中的分數

位置：`member3/analyze.py:151`、`:160`。目前核對 protocol/prompt 指紋，再比較兩份可編輯的結構化 scores，但不重新解析回覆正文。副本中保留原始 TF=10 的回覆，把 receipt.scores 與 evaluation.scores 同時改成 1，`audit_batch` 仍接受。

建議：每個完成回執先以原始回覆解析數值，與結構化 scores 比對；只有明確記錄、可確定重現的格式恢復可例外處理。本輪已另做完整 162 條原文核對，因此沒有發現正式分數被此缺陷影響。

### F3 P2 總審計過度信任舊公平性通過旗標

位置：`member3_extension/merge_results.py:46`。總匯入只讀 `fairness_audit.json` 的 passed。`runtime_context.json` 不在 read_results 的原始 row 指紋內。副本把 runtime_context.snapshot 改成錯誤版本，重新公平性審計會拒絕，但舊 passed 仍為 true，成員三的 raw audit 亦接受。

建議：總匯入時在各批次的正確程式根目錄重新審計，或把所有公平性輸入的指紋綁定到審計記錄並驗證。本輪九個真實批次重新檢查全部通過，未發現正式環境混用。

### F4 P2 有效分數驗證器接受不合法的零分

位置：`member3/analyze.py:45`。`valid_scores` 使用 0–10，但範本及上游 parser 的量尺為 1–10。三項均為 0 的字典會被當成有效分數，可造成缺陷資料被計入均值和完整性。

建議：統計用分數下限改為 1；原始單次 judge 分數另遵守整數約束，彙總均值仍允許小數。新增零分測試。此次正式分數均通過原始 parser，沒有零分進入 162 條結果。
